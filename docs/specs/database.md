# Spec: PostgreSQL Schema

Status: Draft (planned; the Drizzle schema becomes authoritative once written) · Last updated: 2026-09-30 · Related: ADR-0007, ADR-0010, [memory-domain.md](memory-domain.md)

## Authority

Once `services/api/src/**/schema.ts` exists, **the Drizzle schema and migrations are authoritative**, and this document must be kept in sync (AGENTS.md §6). Until then, this is the target design.

## Conventions

- PostgreSQL 17+. `uuid` primary keys (UUIDv7 from clients; `gen_random_uuid()` for server-created rows is acceptable).
- `created_at`, `updated_at` as `timestamptz` on all mutable tables.
- Soft delete via `deleted_at` only where the product needs trash (memories, albums).
- Every foreign key has an index. Enums are Postgres enums, created by migrations.
- Monetary or size counters use `bigint`.

### `storage_objects`
`id uuid PK, owner_id uuid FK, key text unique, bytes bigint, sha256 bytea, ref_count int, created_at`. Unique `(owner_id, sha256, bytes)` enables per-owner dedupe. Objects are deleted by the purge job when `ref_count = 0`.

### `change_log` (sync tombstones)
`seq bigint PK (from change_seq), owner_id, entity (memory|asset|preset|album), entity_id, op (upsert|delete), at`. Index `(owner_id, seq)`. Retention of 90 days, after which clients must do a full resync (documented in sync).

### `presets` (Post, sync)
`id, owner_id, name, experience_id, intent jsonb, profile_id, profile_version, live, source, created_at, updated_at, deleted_at`.

### `idempotency_keys`
`key text, owner_id, route text, response_hash bytea, response jsonb, created_at`. PK `(owner_id, key)`. Purged after 24 h.

### P9: `albums`, `album_members`, `album_invites`, `album_items`
As in [sharing.md](sharing.md). PKs are `(album_id, user_id)` and `(album_id, memory_id)`; indexes on `user_id` and `memory_id`.

### pg-boss
Uses its own `pgboss` schema, managed by the library (ADR-0010).

## Migration policy

- Migrations are generated by `drizzle-kit generate`, reviewed by hand, and committed. Never edit an applied migration.
- Every migration must be forward-only and safe to run on a live database (add column nullable → backfill → constrain in a later migration).
- CI runs all migrations against an empty Postgres and runs schema tests.
- Destructive changes (drop column or table) require an explicit task, and an ADR when they affect data retention.
